Try it: live sandbox

This is the real Aperture dashboard, wired to an in-browser copy of the gateway. Every decision is made by the unmodified controls.rego policy, compiled to WebAssembly, and signed with an Ed25519 key generated for your session. Nothing is sent to a server, and state resets when you reload.

  1. Create a workflow. Run crm.read, then archive.create.
  2. Switch to agent-b and run external.send. It is blocked because of the workflow's history.
  3. Click Approve selected action (the reviewer token is prefilled), then run the send again. Commercial allows it; Federal-adjacent does not.
  4. Open Assurance lab to run live checks, or Evidence & replay to verify the signed chain and download the bundle.

The problem

Agents are being given real tools: CRM reads, file archives, outbound email, access grants, payments. Each call can look harmless on its own. The damage is in the sequence: read a restricted customer record, zip it, send it to an outside address. Per-call permission checks miss that, and a second agent picking up the task can launder it. Security and compliance teams also need proof of what was allowed and why, not just logs.

How Aperture works

01

Gateway

Agents connect over MCP (Model Context Protocol) to Aperture instead of directly to tools. Each agent authenticates and is bound to an operator-created workflow with a budget.

02

Policy with memory

Every proposed call goes to Open Policy Agent together with the workflow's recorded history. Rules match tagged trajectories such as source:restricted → effect:stage → sink:external.

03

Exact approvals

Some rules can be lifted by a separate reviewer. The approval is bound to the exact tool and arguments, expires in minutes and works once. Hard blocks and spend caps cannot be approved away.

04

Signed evidence

Intent is written durably before dispatch. Decisions, inputs and downstream observations form an Ed25519-signed hash chain that exports as a bundle anyone can verify and replay.

One engine, two policy profiles

Rules are data in policies/aperture_data.json, not code. A profile is fixed to a workflow when the workflow is created, so a decision always replays under the rules it was made with.

Assurance: test the control, then check the effect

The assurance suite runs the real gateway and policy against isolated fixtures and inspects the downstream tool ledger to confirm what actually happened. It includes a deliberately broken policy as a negative control, tampering, replay, concurrency and abrupt process kills.

Run the live console

Requires Python 3.10+ and OPA 1.0.1 (the setup script fetches the pinned, checksum-verified release).

python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
python setup.py
python aperture.py        # open http://127.0.0.1:8080

Paste the operator token from data/credentials.json into the dashboard. Run the tests on their own with python assurance.py.

Scope, stated plainly

  • A tested local engineering pilot. Tools, records and identities are synthetic; no real CRM data is read and nothing is sent externally.
  • No production-readiness, latency, compatibility or compliance claim. The federal control mapping is a draft.
  • Signatures prove the captured bytes were not changed. They do not prove that every real-world action was captured.
